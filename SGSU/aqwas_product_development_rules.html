Engineering & architecture rules
ENG-01 P0
All sensor-to-cloud data transmission MUST use TLS 1.3 with mutual certificate authentication. No unencrypted IoT connections permitted in any environment.
Security
ENG-02 P0
Every service must be stateless and horizontally scalable. No service may store session state in memory — use distributed cache (Redis) for shared state.
Scalability
ENG-03 P0
Sensor data ingestion pipeline must be idempotent. Duplicate readings from retry logic must be deduplicated before writing to the time-series store.
Data integrity
ENG-04 P1
Edge compute nodes must perform basic plausibility filtering (pH 0–14, turbidity ≥ 0) before forwarding to cloud. Invalid readings are quarantined, not discarded.
Data quality
ENG-05 P1
All infrastructure must be defined as code (Terraform/CDK). No manual cloud console resource creation. Infrastructure changes require PR review and plan review before apply.
IaC
ENG-06 P1
Database schema changes require a migration script that is backwards-compatible. Zero-downtime deployments must be possible. Breaking migrations are never allowed in a single release.
Database
2
Data & ML model rules
ML-01 P0
Every ML model must be versioned, logged in MLflow, and reproducible from a fixed seed + frozen dependency set. A model that cannot be reproduced cannot be deployed.
MLOps
ML-02 P0
No model may be promoted to production without passing the performance gate: anomaly detection precision ≥ 90%, recall ≥ 85%, evaluated on a held-out labeled dataset.
Quality gate
ML-03 P0
Every alert generated by an AI model MUST include a SHAP-based explanation surfacing the top 3 contributing features in plain language. Black-box alerts are never shipped to operators.
Explainability
ML-04 P1
Training and validation datasets must be split temporally (train on past, validate on future), not randomly. Random splits cause data leakage in time-series models.
Training
ML-05 P1
Model performance is monitored weekly. If RMSE or F1 degrades by more than 10% from the deployment baseline, an automated retraining job is triggered with a blocking review gate.
Monitoring
ML-06 P1
Forecast confidence intervals must always be displayed alongside predicted values. Point forecasts without uncertainty bounds are misleading and are prohibited in the UI.
Uncertainty
3
Alerting & incident response rules
ALERT-01 P0
Emergency-tier (P0) alerts must be delivered within 120 seconds of detection. This is a hard SLA — measured by automated canary tests running continuously in production.
SLA
ALERT-02 P0
Alert notification service must be architecturally independent of the main application. A dashboard outage must never prevent Emergency alerts from reaching operators.
Resilience
ALERT-03 P0
All alerts require acknowledgment with mandatory fields: acknowledged by, action taken, resolution timestamp. An alert cannot be closed without a completed resolution note.
Accountability
ALERT-04 P1
Duplicate alert suppression must deduplicate on the same event within a 15-minute window. Operators must not receive the same alert more than once per active incident.
Deduplication
ALERT-05 P1
Every alert tier (Watch, Advisory, Emergency) must have a distinct visual treatment, sound profile, and notification channel. Operators must never misidentify severity at a glance.
UX clarity
ALERT-06 P2
Escalation paths must be configurable per site: if a primary operator does not acknowledge within N minutes, the system automatically escalates to the defined secondary contact.
Escalation
4
Security & compliance rules
SEC-01 P0
RBAC is mandatory. No user may access data or functionality outside their assigned role. All role assignments are logged and reviewed quarterly.
Access control
SEC-02 P0
MFA is required for all accounts with administrative privileges. Single-factor admin access is a critical security violation in all environments, including staging.
Authentication
SEC-03 P0
The data ingestion pipeline must run anomaly detection on sensor metadata patterns to detect spoofed readings. Cybersecurity threats to IoT sensors are treated at the same severity as water contamination events.
IoT security
SEC-04 P1
All audit logs are immutable, retained for a minimum of 7 years, and stored in a separate account/subscription from the application to prevent tampering.
Audit
SEC-05 P1
A third-party penetration test is required before GA release and annually thereafter. All critical and high-severity findings must be resolved before the test report is closed.
Pen testing
SEC-06 P1
API keys and secrets must never appear in source code, logs, or error messages. All secrets are managed via a secrets manager (e.g., AWS Secrets Manager / HashiCorp Vault).
Secrets mgmt
5
Product & UX rules
UX-01 P0
Every alert and AI output visible to an operator must include a plain-language explanation. Technical model outputs (raw SHAP values, log-odds scores) must never be exposed directly in the operator UI.
Explainability
UX-02 P1
Dashboard must achieve a System Usability Scale (SUS) score of ≥ 75 in UAT with real water utility operators. UX debt that drops this score below 70 blocks the GA release milestone.
Usability
UX-03 P1
All user-facing features must comply with WCAG 2.1 Level AA. Accessibility is not a post-launch retrofit — it is a definition-of-done requirement for every feature.
Accessibility
UX-04 P1
No new major feature may ship without a corresponding onboarding or guided tour update. Operators must never discover critical features accidentally.
Onboarding
UX-05 P2
The dashboard must be fully functional on tablet devices (min 768px viewport). Field technicians use tablets as their primary operational tool.
Responsiveness
UX-06 P2
All geospatial map interactions (zoom, filter, site selection) must complete within 500ms. Slow maps erode operator trust more than any other UI performance issue.
Performance
6
Development process rules
DEV-01 P0
All code changes require at minimum one peer review and must pass the full automated test suite (unit + integration + contract tests) before merging to the main branch. No exceptions.
Code review
DEV-02 P0
Feature flags are required for all features in active development. No feature may reach production in a partially complete state without being behind a disabled flag.
Feature flags
DEV-03 P1
Every new API endpoint must have a contract test. Breaking API changes require a version bump and a deprecation notice with minimum 60-day notice period to existing consumers.
API versioning
DEV-04 P1
Runbooks must exist for every P0 alert condition and every deployment procedure. If an on-call engineer cannot resolve an incident within 30 minutes using the runbook, the runbook is out of date.
Runbooks
DEV-05 P1
All production incidents (P0/P1) require a written post-mortem within 5 business days. Post-mortems are blameless, public within the team, and tracked until all action items are closed.
Post-mortems
DEV-06 P2
Sprint velocity is measured but never used as a performance metric for individuals. The team ships working software, not story points. Estimation accuracy improves via retrospectives, not pressure.
Team health
Priority legend: P0 = Critical / blocks release  ·  P1 = High / must be in v1.0  ·  P2 = Medium / planned for v1.x
